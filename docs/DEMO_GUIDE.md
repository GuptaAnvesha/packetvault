# PacketVault Mid-Check Demo Guide

## How to run the demo

From the project folder, run:

```
powershell -ExecutionPolicy Bypass -File scripts\demo.ps1
```

**Inputs:** none. Just press **Enter** between steps. The script sets the passphrase (`lab-demo-passphrase`) through the `PACKETVAULT_PASSPHRASE` environment variable, so nothing prompts you.

**Before the demo (once):** `pip install -r requirements.txt`

## How the code works behind each step

Every command goes through `packetvault/cli.py`. It reads the arguments and calls the matching `cmd_*` function, which calls the module that does the real work.

### Step 1: Sample (`samplegen.py`, `pcapio.py`)

- `generate_lab_capture()` builds every packet byte by byte: Ethernet header, IPv4 header (with a real checksum), then a TCP, UDP or ICMP header.
- Normal traffic is made by `_http_session()` (full SYN → SYN-ACK → ACK handshake, data, FIN), `_dns_lookup()` and `_ping()`.
- The attacks are `_syn_scan()` (like `nmap -sS`, 1024 ports in 6 s: open ports reply SYN-ACK, closed ports reply RST) and `_connect_scan()` (like `nmap -sT -T2`, 60 ports over 30 s).
- A fixed random seed (7) means the same file is produced every time, so results are repeatable.
- `PcapWriter` writes the standard PCAP format: a 24-byte global header, then for each packet a 16-byte record header (timestamp, length) followed by the raw bytes.
- The scanner IPs are saved in `lab_capture.labels.json`. This is the "ground truth" used in Step 11.

### Step 2: Keygen (`signing.py`)

- `generate_keypair()` calls PyCryptodome's `RSA.generate(2048)` and saves two PEM files: `investigator_private.pem` (kept secret) and `investigator_public.pem` (shared).
- `fingerprint()` is the SHA-256 of the public key, shortened. It's printed so people can confirm they have the right key.

### Step 3: Parse (`pcapio.py`, `parser.py`, `models.py`)

- `iter_frames()` reads the file. It looks at the first 4 bytes ("magic number") to tell classic PCAP from PCAPNG, and which byte order is used.
- `decode_frame()` peels each packet layer by layer:
  - **Ethernet**, the first 14 bytes: destination MAC, source MAC, EtherType (0x0800 = IPv4).
  - **IPv4**: source and destination IPs at bytes 12–20, and the protocol number at byte 9 (6 = TCP, 17 = UDP).
  - **TCP**: ports in the first 4 bytes, flags at byte 13 (SYN = 0x02, ACK = 0x10, etc.).
- The result is a `PacketRecord` (in `models.py`) with 12 fields: index, timestamp, MACs, IPs, protocol, ports, TCP flags, lengths.
- If a packet is malformed, it is still kept with protocol `OTHER`. Evidence is never silently dropped.
- `write_xml()` saves the records as XML. `write_sqlite()` saves them in a database indexed on timestamp and IP pair, so searches are fast.
- If Wireshark is installed, `parse_pcap()` can use Pyshark instead (`--backend pyshark`). Both give the same records.

### Step 4: Seal (`bundle.py` → `chain.py`, `vault_crypto.py`, `detect.py`, `report.py`, `signing.py`)

`seal_case()` runs the whole pipeline in order:

1. **Parse** the PCAP (as in Step 3). It also builds the acquisition metadata: case ID, investigator, time, filename, and the SHA-256 of the original PCAP.
2. **Hash chain** with `chain.seal()`:
   - `genesis_hash()`: H0 = SHA256("PacketVault/v1/H0" + metadata). This ties the chain to this case and this file.
   - `link()`: Hn = SHA256(Hn-1 + canonical bytes of packet n).
   - `canonical_bytes()` (in `models.py`) turns a record into JSON with a fixed field order and no spaces. The same packet always produces the same bytes, and therefore the same hash.
   - Every 256th hash is saved as a **checkpoint**. The last hash is the **root hash**.
3. **Database**: `build_database()` creates the SQLite database **in memory** (`:memory:`), storing each packet with its chain hash. `serialize()` turns it into bytes. Plaintext never touches the disk.
4. **Encrypt** with `vault_crypto.encrypt()`:
   - Generates a random 16-byte **salt** and 12-byte **nonce**.
   - `derive_key()`: PBKDF2-HMAC-SHA256 runs 600,000 rounds on passphrase + salt to produce a 32-byte (256-bit) key.
   - Builds a 38-byte header: `PVLT` + version + cipher ID + iterations + salt + nonce.
   - AES-GCM encrypts the database. The header is passed as **associated data** (`cipher.update(header)`), so it's authenticated but not hidden.
   - Output file = header + ciphertext + 16-byte tag, saved as `evidence.db.enc`.
5. **Detect**: `detect_port_scans()`, explained in Step 11.
6. **Report**: a dictionary containing the metadata, H0, root hash, checkpoints, the SHA-256 of `evidence.db.enc`, traffic statistics and alerts. `serialise()` writes it as JSON with sorted keys, so the bytes are deterministic.
7. **Sign**: `signing.sign()` computes SHA-256 of `report.json` and signs it with the RSA private key using PKCS#1 v1.5, saved as `report.sig`. `render_text()` writes the readable `report.txt`.

### Step 5: Verify (`verify.py`, `chain.py`)

`verify_case()` runs four checks in order, and each one adds a PASS, FAIL or SKIP line:

1. **RSA signature**: `signing.verify()` checks `report.sig` against `report.json` using the public key. If it fails, everything else is skipped, because an unsigned report can't be trusted as a reference.
2. **Container digest**: compares the SHA-256 of `evidence.db.enc` with the value inside the signed report. Checks 1 and 2 need only the public key.
3. **AES-GCM tag**: `vault_crypto.decrypt()` re-derives the key from the passphrase and the stored salt. `decrypt_and_verify()` raises an error if a single bit of the header, ciphertext or tag changed.
4. **Hash chain**: `chain.verify()` rebuilds H0 from the metadata **in the signed report** (not from the database, which an attacker could edit). It then recalculates every Hn and compares each with the stored hash. It also compares the final hash with the signed root, and the record count with the signed count.

### Step 6: Query (`cli.py` → `cmd_query`, `parser.open_database`)

- Decrypts `evidence.db.enc`, then `open_database()` loads the bytes into an in-memory SQLite database with `deserialize()`. No temporary plaintext file is created.
- Filters like `--src` and `--flags` become a SQL `WHERE` clause with `?` placeholders. That's parameterised SQL, so filter values can't inject SQL.

### Step 7: Tamper (`tamper.py`)

- `tamper_case()` plays an insider who knows the passphrase. It decrypts the bundle, changes `dst_port` of record 1500 (351 → 4444), leaves the stored hashes alone, and re-encrypts with the correct passphrase.
- Because the attacker re-encrypted properly, the GCM tag will still pass. Only the hash chain and the signed digest can catch this.

### Step 8: Verify after tampering (`chain.verify`)

- The walk through the chain reaches position 1500. The recomputed H1500 (from the edited record) is not equal to the stored H1500 (from the original), so that's the first divergence.
- The verifier reports `first_divergence = 1500`, which `cli.py` prints as "tampering localised to frame #1500".
- The container digest also fails, because the file bytes changed after re-encryption.

### Step 9: Tamper with recompute (`tamper.py`)

- Mode `recompute` edits record 1500 and then calls `chain.seal()` again, so every stored hash from 1500 onward is rebuilt. The chain inside the database is now self-consistent.

### Step 10: Verify after recompute (`chain._localise_with_checkpoints`)

- No stored hash disagrees with the recomputed chain, so there's no first divergence.
- The recomputed root ≠ the root in the **signed** report → FAIL.
- `_localise_with_checkpoints()` compares the recomputed hash at positions 256, 512, ... with the signed checkpoints. The first mismatch is at 1536 and the previous match was at 1280, so the edit is in positions 1281–1536.
- The attacker can't update the signed report without the RSA private key.

### Step 11: Detect (`detect.py`)

- `_is_probe()` counts only connection attempts: TCP packets with SYN but **not** ACK, or UDP from an ephemeral source port (1024 or above). Server replies (SYN-ACK) are excluded, so a busy server isn't flagged.
- `_max_distinct_in_window()` uses a **sliding window** (two pointers plus a counter). For each host it finds the largest number of distinct destination ports seen within any 10-second span. Over 15 → alert.
- **SYN : SYN-ACK ratio** = SYNs the host sent ÷ SYN-ACKs it received. Normal clients ≈ 1, while the fast scanner got 1024 : 3. If the ratio is 3 or more, the alert is HIGH, otherwise MEDIUM.
- `evaluate()` compares flagged hosts with the labels file and computes true/false positives and negatives, precision, recall, F1 and accuracy.

### Benchmarks (`bench.py`)

- Uses `time.perf_counter()` and takes the median of several runs, which reduces noise.
- Compares AES-CBC/CTR/GCM throughput, MD5/SHA-1/SHA-256 chaining time, and RSA-2048 vs ECC P-256 key generation, signing and verification, over 1k–50k packets. Matplotlib draws the three plots.

### Tests (`tests/`)

- 45 pytest tests: parsing, XML/SQLite round trips, chain localisation, crypto tamper rejection, detection accuracy, and every tamper mode end to end. Run them with `python -m pytest -q`.

## Likely faculty questions

- **Why not just hash the whole file?** It can't tell you where the change is, it doesn't hide anything, and it doesn't prove who collected the evidence.
- **What if the attacker knows the passphrase?** They can decrypt and re-encrypt, but they can't re-sign the report without the private key. The signed root hash and file hash expose them.
- **Why GCM over CBC?** GCM encrypts and authenticates in one step. CBC also needs padding and a separate MAC.
- **Why a salt and 600k iterations?** The salt defeats precomputed password tables. The iterations make brute-force guessing slow.
- **Why is MD5 only in the benchmarks?** MD5 and SHA-1 have practical collision attacks, so they're included only for comparison.
- **Why are H0 values taken from the signed report?** The database is under the attacker's control once they know the passphrase. The signed report is the only trusted reference.
- **Is the data real?** Not yet. It's synthetic lab traffic, and capturing real Nmap traffic in our VirtualBox lab is the next step.
